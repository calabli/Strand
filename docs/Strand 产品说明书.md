# Strand 产品说明书

Nov 12, 2026 · @hichen

## 1. 产品概述

Strand 是一个跨平台的桌面 Git 客户端，功能和布局对照 JetBrains IDE 的 Git 集成，视觉采用 macOS 风格。本文档描述 1.0 版本的功能、交互规则和前后端接口，供前端和后端（核心层）开发使用。

已有一个[可交互原型](https://claude.ai/artifact/CrcYxYiQLe1Cvo9V3vVeak)，覆盖本文档的绝大部分交互。原型用的是假数据，没有接真实的 Git。界面细节以原型为准，规则、数据结构和接口以本文档为准。

### 1.1 目标用户

| 用户 | 主要诉求 |
| --- | --- |
| 习惯 JetBrains Git 界面的开发者 | 不打开 IDE 也能用同样的方式提交、看日志、解决冲突 |
| 使用其他编辑器的开发者 | 需要一个比命令行直观、比现有客户端轻的图形界面 |
| 需要处理大仓库的团队 | 十万级提交的仓库打开和滚动不卡 |

### 1.2 设计原则

这六条是所有功能共同遵守的规则，开发和评审时以此为准。

1. **每个写操作都能撤销。** 提交、合并、变基、重置、丢弃改动等都记入操作日志，可以一步退回。
2. **有风险的操作先说明影响。** 执行前告诉用户会改写几个提交、是否需要强制推送、改动会不会丢。
3. **操作用图标按钮。** 每个图标按钮必须有悬停提示和无障碍标签。只有对话框里的确认按钮和主提交按钮可以带文字。
4. **不可用的操作置灰，不隐藏。** 悬停提示里写明不可用的原因。
5. **提交面板和日志同屏。** 不在“改动”和“历史”之间切换页面。
6. **冲突按修改块处理。** 每个修改块必须被明确标记为接受或舍弃，否则不能完成合并。

### 1.3 术语

| 术语 | 含义 |
| --- | --- |
| 你的 / 对方的 | 冲突时，“你的”指本地当前分支的内容，“对方的”指被合并进来的内容（拉取时是远程分支） |
| 修改块 | 一侧连续改动的若干行，是冲突解决的最小操作单位 |
| 暂存架 | 客户端自己保存的搁置改动，可以命名，按文件搁置，不依赖 Git 的 stash |
| 贮藏 | Git 原生的 stash，一次收起全部改动 |
| 整理提交 | 交互式变基：对一段提交做保留、并入、丢弃、调整顺序 |
| 操作时间线 | 本客户端执行过的写操作列表，用于撤销和重做 |
| 领先 / 落后 | 本地分支比它跟踪的远程分支多出或缺少的提交数 |
| 分离 HEAD | 检出了某个提交或标签，当前不在任何分支上 |

## 2. 系统架构和前后端分工

技术方案已确定为 Tauri 2 + Rust（选型依据见 2.3）：前端运行在系统 WebView 里，核心层用 Rust 实现，两者通过命令和事件通信。前端只负责显示和交互，所有 Git 状态都由核心层计算。

| 层 | 技术 | 职责 |
| --- | --- | --- |
| 前端 | TypeScript + React，虚拟列表，Canvas 画图谱连线，差异和合并编辑器用 CodeMirror 6 | 界面渲染、交互状态（选中、展开、过滤条件）、调用命令、订阅事件 |
| 通信 | Tauri 命令（请求和响应）、Tauri 事件（核心层主动推送）、Channel（大量数据分批传输） | 序列化、分页、任务取消 |
| 核心层：仓库服务 | Rust，tokio 任务调度 | 命令入口、参数校验、任务排队和取消、缓存 |
| 核心层：Git 后端 | gix 负责读，git2 负责本地写，调用系统 git 负责网络和变基 | 读取提交、状态、差异；执行提交、合并、重置；抓取、拉取、推送 |
| 核心层：图谱布局 | Rust | 计算每个提交所在的泳道和连线，只返回可视范围 |
| 核心层：文件监听 | notify | 工作区和 `.git` 变化时增量刷新，并向前端发事件 |
| 核心层：操作日志 | Rust，本地 SQLite 或 JSON 文件 | 记录每次写操作前后的引用位置，支撑撤销和重做 |

### 2.1 前后端约定

- **前端不推算 Git 状态。** 领先落后数、是否可重置、某个提交是否已推送等，都由核心层返回。
- **所有列表分页。** 提交列表、差异行、追溯结果都按范围请求，前端用虚拟滚动。
- **长任务可取消。** 核心层为每个长任务返回 `task_id`，前端可以调用 `task_cancel`。用户切换分支或仓库时，前端必须取消未完成的读任务。
- **写操作串行。** 同一个仓库同一时间只执行一个写操作，其余排队。
- **写操作返回操作编号。** 每个写命令成功后返回 `op_id`，同时核心层发出 `repo_changed` 事件，前端据此刷新受影响的区域。
- **错误结构统一。** 所有命令失败时返回 `{ code, message, detail }`。`code` 是固定的枚举，前端按 `code` 决定提示方式，`message` 是可以直接显示的中文说明。

### 2.2 核心层事件

| 事件 | 触发时机 | 前端处理 |
| --- | --- | --- |
| `repo_changed` | 引用、索引或工作区发生变化 | 载荷里的 `scopes` 说明变了什么（`refs`、`status`、`stash`、`shelf`），只刷新对应区域 |
| `task_progress` | 长任务有进度 | 更新进度显示 |
| `task_done` | 长任务结束 | 成功则显示结果，失败则按错误码提示 |
| `merge_state` | 进入或离开合并、变基状态 | 切换工具栏的“进行中”提示，决定是否打开冲突列表 |

### 2.3 技术选型

目标平台是 macOS 和 Windows。方案定为 **Tauri 2 + Rust**，主要理由有三条：

- 现有的可交互原型是 Web 技术写的，界面可以直接沿用，不用重写。
- 性能瓶颈（大仓库的日志、状态、差异、追溯）都落在核心层，用 Rust 实现可以多线程处理。
- 使用系统自带的 WebView，安装包小，空闲内存占用低。

候选方案对比如下。体积是大致量级，不是实测值。

| 方案 | 性能 | 安装包体积 | 能否沿用原型 | 主要问题 | 结论 |
| --- | --- | --- | --- | --- | --- |
| Tauri 2 + Rust | 核心快，界面取决于系统 WebView | 小（十几 MB 量级） | 能 | 两个平台的 WebView 内核不同，要分别测试 | 采用 |
| Electron + Node | 界面一致，Git 重计算要另写原生模块 | 大（上百 MB） | 能 | 内存占用高 | 不采用；团队无法投入 Rust 时的备选 |
| GPUI | 最好 | 小 | 不能，界面全部重写 | 接口不稳定，现成组件和文档少 | 不采用 |
| Qt 或 Flutter | 好 | 中 | 不能 | macOS 风格要自己绘制；Flutter 桌面端文本编辑偏弱 | 不采用 |
| 两个平台各写原生 | 最好 | 小 | 不能 | 两套代码，工作量翻倍 | 不采用 |

各部分的具体选型：

| 部分 | 选型 | 说明 |
| --- | --- | --- |
| Git 读取（日志、状态、差异、追溯） | gix | 纯 Rust，可多线程。目前只用于日志，工作区状态和差异暂用 git2 |
| Git 本地写入（提交、分支、重置、贮藏） | git2 | 功能完整，行为稳定。也负责工作区状态和差异 |
| 网络和变基（抓取、拉取、推送、交互式变基） | 调用系统 git | 直接复用用户已有的 SSH 密钥和凭据管理器，核心层不处理认证。提交也调用系统 git，这样钩子、签名、换行符转换和命令行一致 |
| 界面框架 | React + TypeScript | 生态成熟，可用的组件和熟悉它的开发者最多 |
| 提交列表和图谱 | 虚拟滚动 + Canvas | 只把可见范围的数据从核心层传到前端 |
| 差异和三栏合并 | CodeMirror 6 | 比 Monaco 轻，自带合并视图扩展 |
| 文件监听 | notify | 仓库变化后增量刷新 |

两个平台需要分别处理的地方：

| 事项 | macOS | Windows |
| --- | --- | --- |
| WebView 内核 | WebKit | WebView2（Chromium）。滚动、字体渲染和部分 CSS 表现与 WebKit 有差异，每个界面改动都要在两个平台上验证 |
| 窗口外观 | 左上角红绿灯按钮，侧栏毛玻璃 | 右上角窗口按钮，Mica 材质。标题栏按平台各做一套 |
| 系统 Git | 通常已随开发者工具安装 | 可能没有安装。安装包不附带 Git，默认用户自行安装；启动时检测不到就提示并给出下载地址 |
| 文件系统 | 无特殊处理 | 换行符转换、长路径、文件被占用时无法改写，核心层要专门处理 |
| 签名和分发 | 开发者证书签名并公证 | 代码签名证书，否则安装时会被系统拦截 |

### 2.4 启动和仓库命令

应用启动时先调用 `git_check`；通过后自动打开上次的仓库（路径存在前端本地），失败则显示“打开一个仓库”页。

| 命令 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `git_check` | 无 | `GitInfo` | 检测系统 Git。`ok` 为假时前端显示“没有找到 Git”或“Git 版本过低”，不进入主界面 |
| `repo_open` | `path` | `RepoState` | 从 `path` 向上查找仓库根目录并打开，同时读取日志和计算图谱；失败返回 `NOT_A_REPO` |
| `repo_state` | 无 | `RepoState` | 当前分支、HEAD 和进行中的操作 |
| `repo_reload` | 无 | `RepoState` | 重新读取引用、日志和图谱。现在由工具栏的刷新按钮触发，文件监听实现后改为自动 |

这些命令都在后台线程执行。打开仓库时只读日志的结构（编号、父提交、提交时间），据此排序并算好图谱；说明、作者等内容由 log\_query 按页读取。提交数不少于 2000 且仓库没有 commit-graph 文件时，打开后在后台运行 git commit-graph write --reachable 生成一份；仓库配置了 core.commitGraph = false 时不生成。

### 2.5 开发进度

下表按本文档各节的顺序记录核心层的命令和事件、实现状态，以及它们和本文档规定的差别；每个命令只出现一次。没有列出的命令都还没有实现。

| 命令或事件 | 状态 | 和文档的差别 |
| --- | --- | --- |
| git\_check、repo\_open、repo\_state、repo\_reload | 已实现 | RepoState.state 另有 unstashing（取回贮藏或暂存架时有冲突）；没有 pull\_mode（默认拉取方式由前端按仓库保存） |
| launch\_path | 已实现 | 新增：读取启动参数里的仓库路径，strand /path/to/repo 直接打开该仓库，优先于上次打开的仓库 |
| 事件 repo\_changed | 已实现 | scopes 有 refs、status、stash、shelf 四种（stash 是 refs/stash，shelf 是 .git/strand/shelf/，只刷新对应的列表）；事件在 300 ms 内合并；.gitignore 忽略的文件不触发 |
| status\_get | 已实现 | 返回 WorktreeStatus { changes: \[FileChange\], untracked: \[path\] }。changes 是已跟踪文件相对 HEAD 的改动，不区分是否已暂存；状态可能是 T（类型变化），界面按 M 显示 |
| diff\_worktree | 已实现 | 返回 FileDiff { path, binary, hunks, truncated }；未跟踪的文件显示为全部新增；单个文件超过 2 万行时截断 |
| commit\_create | 已实现 | 返回 { id, state, op? }，op 是写进操作日志的那一条，代替 op\_id。提交前校验合并状态、空说明、空选择；重命名时旧路径一起提交。Selection 的文件带 whole 和 lines: \[{ hunk, line }\]，行号对应 diff\_worktree(path, 不忽略空白, 3 行上下文)。有部分勾选时在一个临时索引里按 HEAD 搭好要提交的内容（部分文件按原始字节拼出，保留换行符和文件末尾有没有换行），用 GIT\_INDEX\_FILE 运行 git commit（照常跑钩子），再把真正的索引里这些路径对齐到新 HEAD。行级勾选只对已修改的文本文件有效；文件已经变了时返回 INVALID\_RANGE |
| commit\_amend | 已实现 | 入参 message?、selection、sign\_off?；message 为空时保留原说明，selection 可以为空（只改说明）。返回 { id, state, op? }。只作用于上一次提交，已推送时返回 ALREADY\_PUSHED；更早的提交用 commit\_fixup。整文件用 git commit --amend --only，部分行用临时索引加 --amend |
| changes\_discard、untracked\_add、untracked\_ignore、untracked\_delete | 已实现 | changes\_discard 用 git restore --source=HEAD --staged --worktree，记入操作日志。untracked\_ignore 把 /路径 追加到根目录 .gitignore（不重复），untracked\_delete 移到系统废纸篓。三个未跟踪文件操作都记入操作日志、可以撤销：快照额外记下涉及的文件（加入版本控制和删除记下这个文件，加入忽略规则记下 .gitignore） |
| stash\_list、stash\_files、stash\_push、stash\_apply、stash\_drop | 已实现 | pop 和 apply 合成 stash\_apply（index、drop）。stash\_files 新增，列出贮藏里改动的文件，文件差异用 diff\_commit（贮藏的提交哈希）。stash\_push 没有改动时返回 NOTHING\_SELECTED。取回冲突返回 CONFLICTS，仓库状态变为新增的 unstashing，merge\_session 的 kind 为 unstash；工作区改动会被覆盖时返回 WORKTREE\_CONFLICT。写操作返回 { result, state, op? } |
| shelf\_list、shelf\_save、shelf\_restore、shelf\_delete、shelf\_rename、shelf\_files、shelf\_diff | 已实现 | shelf\_save 的 paths 含重命名的旧路径，name 为空时用“改动 · 序号”；补丁用 git diff HEAD --binary 生成，先写补丁再用 git restore 把文件改回 HEAD。shelf\_restore 用 git apply --3way，冲突时同贮藏；可选入参 paths 只取回这些文件，剩下的另存成同名新条目（新编号），paths 为空或都不在条目里返回 NOTHING\_SELECTED，全选时等同于不带 paths。shelf\_rename、shelf\_files、shelf\_diff 是新增的：shelf\_rename 不记入操作日志；shelf\_files(id) 返回 FileChange\[\]（含改动行数），shelf\_diff(id, path) 返回 FileDiff，都从 .git/strand/shelf/\<id>.patch 解析，条目已删除或条目里没有这个文件时返回 NOT\_FOUND |
| checks\_config\_get、checks\_config\_set、checks\_run | 已实现 | 新增（提交前检查）。配置存在仓库 Git 配置的 strand.\* 键里，读取时附带按仓库文件推测的建议命令。checks\_run(task\_id, kind, files) 每次运行一种（format 或 check），在仓库锁外面跑，可以用 task\_cancel 取消，最长 5 分钟；返回 ok、退出码、输出（最多 64 KB，去掉颜色控制符）、认出的问题 issues\[{path, line, col, level, message}\]、格式化改动了的文件 changed\[\] |
| log\_query | 已实现 | 分页、过滤和排序。不过滤时子提交一定在父提交前面，其余按提交时间从新到旧（同 git log --date-order）；日志里的 Commit 带 unpushed（从当前分支能到达、但不在它的跟踪分支里；没有跟踪分支时按不在任何远程分支里算）。便宜的条件先算（分支可达、日期、作者、路径），最后才在多个线程上解码剩下的提交匹配说明文字。作者和作者时间第一次用到时读一遍全部提交并缓存；上一次的过滤结果也缓存，翻页不重算。不是正则时，4 位以上的十六进制文字还匹配哈希前缀。日期按作者时间，按时间排序按提交时间。路径过滤在全部引用上运行一次 git rev-list，在仓库锁外面计算后缓存。8.6 万提交的 git.git 上：搜索约 100 ms，作者、日期、排序 10 ms 以内。首批结果先返回、其余分批追加：路径过滤的 git rev-list 在后台线程里跑、边读边记，第一次查询最多等 200 ms（攒够 200 个就返回），之后每次查询用目前找到的结果过滤；说明文字按 8192 行一块扫描，每次查询最多扫 150 ms。没算完时 LogPage.partial 为真，total 是目前的数目，界面每 300 ms 把已加载的页重新查一遍。git.git 上按 builtin/ 过滤：第一次查询 166 ms 带回 256 个，约 5 秒后找全 14401 个 |
| log\_authors | 已实现 | 新增：作者过滤的选项，返回 \[{ name, email, count }\]，按提交数从多到少；同一邮箱（不区分大小写）算一个作者，名字取最近一次用的 |
| log\_locate | 已实现 | 新增：传分支名、标签名、哈希前缀或 HEAD，返回它在日志里的行号，供分支树单击、“定位”和跳到提交使用；可选的 filter、sort 时返回在过滤结果里的行号，不在结果里返回 null，换过滤条件后用它保留选中的提交。说明书里的 commit\_find 没有单独做，用它代替 |
| commit\_detail、diff\_commit | 已实现 | commit\_detail 返回 { commit, files, caps }，合并提交相对第一个父提交；diff\_commit 返回 FileDiff |
| commit\_caps | 已实现 | 新增：只取可用条件（右键菜单、多选用）。caps 含 cherry\_pick、checkout、reset、revert、undo、reword、drop、rebase\_from、fixup、compare\_local、push\_to，每项 { ok, why? }；另带 parent、child（用于 → / ← 和跳转图标）和 web\_url。web\_url 按 origin 的地址（https、ssh://、git@host:path 三种写法）拼出托管平台上这个提交的页面：GitLab 用 /-/commit/，Bitbucket 用 /commits/，GitHub、Gitee、Codeberg、Gitea 用 /commit/；认不出平台时为空，地址里的用户名和密码会去掉 |

## 4. 提交面板

提交面板固定在窗口左侧，有三个标签页：提交、暂存架、贮藏。用户不直接操作 Git 的暂存区：勾选的文件和行就是这次要提交的内容，没勾的留在工作区。

### 4.1 “提交”标签页的组成

从上到下依次是：

1. **工具图标行**：刷新、回滚、查看差异、直接搁置、创建补丁、按目录分组、展开、折叠。
2. **“改动”节点**：带全选勾选框、折叠箭头、“已选 a / b”计数。
3. **文件行**：勾选框、状态字母、路径、新增和删除行数、丢弃图标。
4. **“未跟踪的文件”分组**：每个文件有加入版本控制、加入忽略规则、删除三个图标。
5. **提交说明区**：标题字数计数、输入框、修订选项、说明历史、生成说明、提交选项。
6. **按钮行**：提交（主按钮，带文字）、提交并推送、搁置到暂存架、贮藏。

没有改动时，文件列表显示“没有改动，工作区是干净的”，提交说明区和按钮行整体隐藏。

### 4.2 文件状态

| 字母 | 含义 | 颜色 |
| --- | --- | --- |
| M | 已修改 | 蓝 |
| A | 新增（已加入版本控制） | 绿 |
| D | 已删除 | 红 |
| R | 已重命名，路径显示为“旧路径 → 新路径” | 蓝 |
| ? | 未跟踪，只出现在“未跟踪的文件”分组 | 灰 |

### 4.3 勾选规则

- 新出现的已跟踪改动默认勾选；刚加入版本控制的文件默认勾选。
- 文件勾选框有三态：全选、部分（只选了部分行）、不选。点击部分态变为全选。
- “改动”节点的勾选框：全部勾选时点击变为全不选，其余情况点击变为全选。
- 行级勾选在差异标签页里操作（见第 10 节），只对状态为 M 的文件有效。
- 勾选状态存在前端，按“文件路径 + 修改块序号 + 行序号”记录。文件内容变化后，该文件的行级勾选重置为全选。

### 4.4 提交

| 校验 | 不通过时 |
| --- | --- |
| 仓库不在合并或变基进行中 | 提示“合并还没完成，先解决冲突或中止拉取” |
| 至少勾选一个文件 | 提示“至少勾选一个文件” |
| 非修订时，说明的第一行不为空 | 提示“先写一句提交说明”，焦点移到输入框 |
| 修订的目标提交还没推送 | 提示“上一次提交已经推送，不能修订” |

校验通过后的流程：

1. 按提交选项执行提交前步骤（格式化、检查）。检查失败时显示问题列表，用户可以选择仍然提交或取消。
2. 核心层按勾选内容构造索引并创建提交。
3. 新提交出现在日志最上方并被选中，领先数加一。
4. 已提交的文件从列表移除；只提交了部分行的文件留在列表里，显示剩余的改动。
5. 说明输入框清空，这条说明记入说明历史。
6. 底部提示“已提交 N 个文件”，带撤销图标。

说明的第一行是标题，空一行后是正文。标题超过 50 字时计数变为警示色，但不阻止提交。快捷键 ⌘↵。

### 4.5 修订

- 勾选“修订”后，旁边出现下拉框，列出当前分支上还没推送的提交，默认选中上一次提交。
- 目标是上一次提交：勾选的改动并入该提交；说明不为空则替换原说明，为空则保留原说明。
- 目标是更早的提交：等同于对该提交执行 Fixup（见第 9 节），它之后的提交会被改写。
- 主按钮文字从“提交”变为“修订”。

### 4.6 提交说明的辅助功能

| 功能 | 规则 |
| --- | --- |
| 说明历史 | 保留最近 10 条，去重，最新的在前；点击某一条填入输入框并覆盖当前内容；按仓库保存在本地 |
| 生成说明 | 1.0 按规则拼接：“修改/新增 + 文件名 + 涉及目录 + 行数”；生成后提示用户自行修改。接入 AI 生成列入后续版本 |
| 提交选项 | 三个开关：提交前格式化代码、提交前运行检查（默认开）、在说明末尾加签名行；按仓库保存 |

### 4.7 工具图标行

| 图标 | 可用条件 | 行为 |
| --- | --- | --- |
| 刷新 | 始终 | 重新读取工作区状态 |
| 回滚 | 至少勾选一个文件 | 弹出确认，确认后丢弃勾选文件的改动 |
| 查看差异 | 有改动 | 打开第一个勾选文件的差异标签页 |
| 直接搁置 | 至少勾选一个文件 | 不询问名字，用“改动 · 序号”命名并搁置 |
| 创建补丁 | 至少勾选一个文件 | 打开补丁窗口（见第 10 节） |
| 按目录分组 | 始终 | 文件按所在目录分组显示；该设置同时作用于提交详情里的文件列表 |
| 展开 / 折叠 | 始终 | 展开或折叠“改动”节点 |

### 4.8 未跟踪的文件

| 操作 | 结果 |
| --- | --- |
| 加入版本控制 | 文件移到“改动”里，状态为 A，默认勾选 |
| 加入忽略规则 | 把路径追加到仓库根目录的 `.gitignore`，文件从列表消失；`.gitignore` 本身会出现在“改动”里 |
| 删除 | 从磁盘删除文件，移到系统废纸篓而不是直接删除 |

### 4.9 暂存架和贮藏

两者都用来把改动先收起来，区别如下。

|  | 暂存架 | 贮藏 |
| --- | --- | --- |
| 实现 | 客户端自己保存补丁文件 | Git 原生 stash |
| 范围 | 勾选的文件 | 全部已跟踪的改动 |
| 命名 | 用户输入，或直接搁置时自动命名 | 自动：`WIP on <分支>：<短哈希> <说明>` |
| 取回 | 取回到工作区，条目删除 | 两种：取回并删除（pop）、取回但保留（apply） |
| 其他工具可见 | 否 | 是，命令行 `git stash list` 可见 |

取回时如果和工作区现有改动冲突，进入冲突解决流程（第 8 节），“你的”是工作区，“对方的”是取回的内容。

### 4.10 后端命令

| 命令 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `status_get` | 无 | `changes[]`、`untracked[]` | 每个文件带状态、新增和删除行数 |
| `diff_worktree` | `path` | `hunks[]` | 工作区相对 HEAD 的差异，按修改块返回 |
| `commit_create` | `message`、`selection`、`sign_off` | `op_id`、`commit` | `selection` 为每个文件的整文件或行范围；核心层据此构造索引 |
| `commit_amend` | `message?`、`selection` | `op_id`、`commit` | 只作用于上一次提交；目标已推送时返回 `ALREADY_PUSHED` |
| `checks_run` | `kinds[]` | `issues[]` | 提交前格式化和检查；命令在仓库配置里定义 |
| `changes_discard` | `paths[]` | `op_id` | 丢弃前把内容存入操作日志，供撤销 |
| `untracked_add` / `untracked_ignore` / `untracked_delete` | `path` | `op_id` | 对应 4.8 的三个操作 |
| `shelf_list` / `shelf_save` / `shelf_restore` / `shelf_delete` | `name`、`paths[]` 或 `id` | 列表或 `op_id` | 补丁存在应用数据目录，按仓库分开 |
| `stash_list` / `stash_push` / `stash_pop` / `stash_apply` / `stash_drop` | `index` | 列表或 `op_id` | 直接对应 `git stash` |

## 5. Git 日志

Git 日志是主区域的默认标签页，由分支树、提交列表、提交详情三栏组成。分支树见第 6 节，本节描述提交列表、提交详情和控制台。

### 5.1 过滤栏

多个过滤条件同时生效，取交集。任何过滤或排序生效时，图谱连线隐藏，只显示平铺的提交行。

| 控件 | 规则 |
| --- | --- |
| 分支树开关 | 显示或隐藏分支树 |
| 搜索框 | 匹配提交说明、正文和哈希；输入后实时过滤，防抖 150 ms |
| `.*` 开关 | 打开后按正则表达式匹配；表达式非法时结果为空，输入框变为错误样式 |
| `Cc` 开关 | 打开后区分大小写，默认不区分 |
| 分支 | 只显示从该分支能到达的提交；和分支树里点选分支是同一个状态 |
| 作者 | 单选，选项来自仓库里出现过的作者 |
| 日期 | 所有日期、今天、最近 3 天、最近 6 天；后续版本支持自定义范围 |
| 路径 | 子串匹配，只显示改过匹配文件的提交；在提交详情里点文件会自动填入 |
| 按时间排序 | 打开后按提交时间倒序，关闭时按图谱（拓扑）顺序 |
| 刷新 | 重新读取日志 |
| 拣选 | 对当前选中的提交执行拣选 |
| 显示选项 | 三个开关：显示精确日期、本地和远程在同一提交时合并标签、合并提交显示为灰色；默认都打开 |
| 跳到提交 | 输入哈希前缀、分支名或标签名，选中对应提交并清空过滤条件；找不到时提示 |
| 整理提交 | 打开整理窗口（见第 9 节） |

### 5.2 提交行

每行从左到右：图谱节点、引用标签、提交说明标题、“未推送”标记、作者、日期。

- **日期**：默认显示 `年/月/日 时:分`；关闭“显示精确日期”后显示相对时间（如“2 分钟前”）。
- **合并提交**：有两个及以上父提交的行，说明文字变灰。
- **未推送**：从当前分支能到达、但不在其跟踪的远程分支里的提交。
- **引用标签**的显示规则见下表。

| 情况 | 标签 |
| --- | --- |
| 当前分支指向该提交 | 深色底的分支名 |
| 其他本地分支指向该提交 | 蓝色底的分支名 |
| 本地分支和它跟踪的远程分支指向同一提交 | 合并为 `origin & <分支名>` |
| 远程分支单独指向该提交 | 灰色底的 `origin/<分支名>` |
| 标签指向该提交 | 黄色底的标签名 |

标签过多放不下时截断并显示省略号，悬停显示完整列表。

### 5.3 图谱

- 每个提交占一个泳道，泳道间距 18 px，行高 36 px。泳道分配由核心层计算，前端只负责绘制。
- 同泳道的父子提交用竖线连接。第一父提交在别的泳道时，先竖直到父提交的上一行再弯过去；第二父提交（合并进来的一侧）先弯到对方泳道再竖直向下。
- 当前分支的最新提交用空心圆表示，其余用实心圆。
- 泳道颜色按泳道序号循环取 4 种颜色。
- 长连线折叠：子提交到父提交跨过超过 30 行的线，从子提交往下画 4 行后用向下的箭头收住，这条泳道让给别的线；到父提交上方 4 行时重新占一条泳道，从顶部的箭头接回来。父提交不在列表里的长线只收不接。分支多的仓库里大部分泳道都是这种跨过几千行的线，折叠后图谱宽度降到十几条。点箭头跳到线的另一头并选中那一行：向下的箭头跳到父提交，接回来的箭头跳到这条线出发的子提交。
- 性能要求：列表用虚拟滚动，连线用 Canvas 绘制；前端按可视范围向核心层请求，每次 200 行，前后各预取一页。

### 5.4 选中和多选

| 操作 | 结果 |
| --- | --- |
| 单击 | 选中该提交，清除多选 |
| ⌘ 或 Ctrl + 单击 | 加选或取消加选 |
| Shift + 单击 | 选中从上次选中到本次点击之间的所有提交 |
| 右键 | 选中该提交并打开右键菜单；右键点在多选范围内时保留多选 |
| → | 跳到第一父提交 |
| ← | 跳到子提交；有多个子提交时取以它为第一父提交的那个 |
| F2 | 修改选中提交的说明（满足可用条件时） |

选中两个及以上提交时，提交详情栏改为显示“已选 N 个提交”和批量操作：全部拣选、压缩成一个、丢弃、取消多选。

### 5.5 提交详情

右侧详情栏分上下两块。

- **上半：改动文件。** 标题行显示文件数，右侧四个图标：按目录分组、和本地比较、创建补丁、查看这个版本时的仓库。每个文件显示状态字母、路径、新增和删除行数；点击文件把路径填入路径过滤；文件右侧有逐行追溯图标。
- **下半：提交信息。** 说明标题和正文、作者头像和姓名、精确日期和相对时间、哈希（点击复制）、一排操作图标。

### 5.6 提交操作和可用条件

所有操作同时出现在详情栏的图标行和右键菜单里。可用条件由核心层随提交数据一起返回（`caps` 字段），前端只负责置灰和显示原因。仓库处于合并或变基进行中时，除复制和查看类操作外全部不可用。

| 操作 | 可用条件 | 结果 |
| --- | --- | --- |
| 复制版本号 | 始终 | 完整哈希写入剪贴板 |
| 创建补丁 | 始终 | 打开补丁窗口 |
| 拣选 | 该提交不在当前分支的历史里 | 在当前分支顶端新建一个内容相同的提交；有冲突时进入冲突解决 |
| 检出这个版本 | 始终 | 进入分离 HEAD 状态 |
| 查看这个版本时的仓库 | 始终 | 打开只读的文件树窗口 |
| 和本地比较 | 该提交不是当前分支的最新提交 | 以该提交为起点、当前分支最新提交为终点进入比较（见第 10 节） |
| 重置当前分支到这里 | 该提交在当前分支历史里、不是最新提交、它之后的提交全部未推送 | 弹出重置方式对话框：软、混合（默认）、硬 |
| 还原提交 | 该提交在当前分支历史里 | 新建一个提交撤掉它的改动，说明为“还原“原说明”” |
| 撤销提交 | 该提交是当前分支的最新提交且未推送 | 去掉提交，改动放回工作区并保持勾选 |
| 修改提交说明 | 同上 | 弹出输入框，预填原说明；为空时不允许确定 |
| Fixup | 该提交在当前分支的未推送段里，且提交面板有勾选的改动 | 勾选的改动并入该提交，说明不变 |
| Squash Into | 同上 | 勾选的改动并入该提交，并弹出输入框修改说明 |
| 丢弃提交 | 该提交在当前分支的未推送段里 | 从历史里去掉该提交和它的改动 |
| 压缩提交 | 多选，且选中的提交在未推送段里相邻 | 合并成一个提交，说明取最早的那个，其余说明并入正文 |
| 从这里开始整理 | 该提交在可整理范围内且不是最新提交 | 打开整理窗口，范围为该提交到最新提交 |
| 推送到这里为止 | 该提交在未推送段里，且远程没有新提交、不需要强制推送 | 只推送到该提交，它之后的提交仍为未推送 |
| 分支子菜单 | 始终 | 打开指向该提交的分支（没有则为当前分支）的子菜单 |
| 新建分支 / 新建标签 | 始终 | 弹出输入框，在该提交上创建 |
| 设为比较起点 | 始终 | 进入比较模式，再点另一个提交显示比较结果 |
| 跳到子提交 / 父提交 | 存在对应提交 | 选中并滚动到该提交 |
| 在浏览器中查看 | 仓库的远程地址能识别出托管平台 | 用系统浏览器打开该提交的页面 |

“未推送段”指从当前分支最新提交沿第一父提交往回走，连续的、未推送的、非合并的提交。

### 5.7 重置方式

| 方式 | 被移除的提交里的改动 |
| --- | --- |
| 软重置 | 放回工作区，保持勾选，可以直接重新提交 |
| 混合重置（默认） | 放回工作区，不勾选 |
| 硬重置 | 丢弃；对话框用红色确认按钮 |

三种方式都记入操作日志，可以撤销。

### 5.8 控制台

主区域的第二个标签页，按时间顺序显示核心层执行过的 Git 命令。

- 以 `#` 开头的行是客户端自己的操作（如搁置、撤销），没有直接对应的 Git 命令。
- 保留最近 300 行，可以清空。控制台内容不随撤销回退。
- 命令里的凭据必须打码。

## 6. 分支、标签和工作目录

分支操作有三个入口：日志左侧的分支树、工具栏的分支弹窗、分支上的右键菜单。三处调用的是同一组操作，规则一致。

### 6.1 分支树

分支树左边是一列操作图标，右边从上到下是：搜索框、“HEAD（当前分支）”、本地、远程、标签、工作目录。四个分组都可以折叠。

| 交互 | 结果 |
| --- | --- |
| 搜索框输入 | 按名称子串过滤分支、远程分支和标签，不区分大小写 |
| 单击分支 | 日志只显示该分支的提交，该分支行高亮；再点一次取消 |
| 单击“HEAD（当前分支）” | 等同于单击当前分支 |
| 双击分支 | 切换到该分支 |
| 拖动分支到另一个分支上 | 弹出确认，把被拖的分支合并到目标分支；目标不是当前分支时先切换过去 |
| 悬停分支 | 出现切换、合并到当前分支、和当前分支比较、收藏四个图标 |
| 右键分支 | 打开分支菜单（见 6.4） |
| 单击标签 | 选中并滚动到标签所在的提交 |
| 远程分支上的箭头图标 | 检出为本地分支 |

当前分支加粗并带“当前”标记；收藏的分支名前显示星标，在分支弹窗里排在前面。

左侧操作图标列（“选中的分支”指在树里单击高亮的那个）：

| 图标 | 可用条件 | 行为 |
| --- | --- | --- |
| 新建分支 | 始终 | 从当前位置新建 |
| 更新 | 不在合并或变基中 | 拉取当前分支 |
| 删除 | 选中了一个非当前分支 | 删除选中的分支 |
| 比较 | 选中了一个非当前分支 | 和当前分支比较 |
| 抓取 | 始终 | 抓取所有远程 |
| 收藏 | 始终 | 切换选中分支（没有选中则为当前分支）的收藏状态 |
| 定位 | 始终 | 清空过滤条件，选中当前分支的最新提交 |
| 全部展开 / 全部折叠 | 始终 | 作用于四个分组 |

### 6.2 分支弹窗

点工具栏的分支按钮打开。顶部是搜索框，下面是一个可用方向键选择、回车执行的列表。

1. **常用操作**：更新项目（拉取）、提交、推送、抓取、新建分支、新建工作目录、检出标签或指定版本。
2. **本地分支**：收藏的在前；每行右侧显示它跟踪的远程分支，没有则显示“本地”。选中后进入该分支的子菜单。
3. **远程分支**：选中后检出为本地分支。

搜索框有输入时，除了过滤上面的项，还会列出跨分支的操作，例如“把 main 合并到当前分支”“把当前分支变基到 main 之上”“和 main 比较”。

分支子菜单的第一项是“返回”。其余项：

| 分支 | 子菜单项 |
| --- | --- |
| 非当前分支 | 检出、合并到当前分支、把当前分支变基到它之上、和当前分支比较、从它新建分支、只看它的提交、收藏、重命名、删除 |
| 当前分支 | 更新（拉取）、推送、从它新建分支、只看它的提交、收藏、重命名 |

### 6.3 分支操作规则

| 操作 | 校验和前置条件 | 结果 |
| --- | --- | --- |
| 新建分支 | 名字不为空、不含空格、不和现有分支重名、符合 Git 引用命名规则 | 在指定提交（默认当前位置）创建并切换过去；输入框预填 `feature/` |
| 切换分支 | 不在合并或变基中；工作区改动和目标分支不冲突 | 工作区改动带到新分支；有冲突时询问：先贮藏再切换，或取消 |
| 重命名 | 同新建分支的命名校验 | 只改本地名字；已推送的分支提示远程名字不会跟着变 |
| 删除 | 不能删除当前分支 | 弹出确认；分支上有未合并的提交时在确认框里说明 |
| 合并到当前分支 | 不在合并或变基中 | 三种结果：已包含则提示无需合并；能快进则快进；否则生成合并提交，有冲突时进入冲突解决 |
| 变基到某分支之上 | 当前分支独有的提交里没有合并提交 | 弹出确认；独有提交被改写并接到目标分支最新提交之后；改写了已推送的提交时，分支标记为“需要强制推送” |
| 检出远程分支 | — | 同名本地分支已存在则切换过去；否则新建同名本地分支并设置跟踪 |
| 检出标签或指定版本 | 输入标签名或哈希前缀，找不到时提示 | 进入分离 HEAD；切换到任意分支后退出该状态 |
| 收藏 | — | 只影响显示顺序，按仓库保存在本地 |

### 6.4 分支右键菜单

切换到这个分支、合并到当前分支、把当前分支变基到它之上、和当前分支比较、收藏、只看这个分支的提交、从这里新建分支、重命名、删除。对当前分支，前四项和“删除”置灰。

### 6.5 标签

| 操作 | 规则 |
| --- | --- |
| 新建 | 在选中的提交上创建；名字不为空、不含空格、不重名；1.0 只支持轻量标签，带说明的标签列入后续版本 |
| 推送 | 未推送的标签在树里显示推送图标；也可以在推送对话框里勾选“同时推送标签” |
| 删除 | 只删除本地标签；已推送的标签在确认框里说明远程仍然保留 |

### 6.6 工作目录

工作目录让同一个仓库在另一个文件夹里同时检出另一个分支。

- 新建：输入文件夹路径和要检出的分支。路径已存在且非空时报错；同一个分支不能同时被两个工作目录检出。
- 列表：显示路径和所在分支。
- 移除：目录里有未提交改动时在确认框里警告。
- 1.0 不支持在客户端内切换到另一个工作目录，只提供“在文件管理器中显示”。

### 6.7 后端命令

| 命令 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `refs_list` | 无 | `branches[]`、`remotes[]`、`tags[]`、`worktrees[]`、`head` | 分支带领先落后数、跟踪的远程分支、是否需要强制推送 |
| `branch_create` | `name`、`at?`、`checkout` | `op_id` |  |
| `branch_switch` | `name`、`stash_first?` | `op_id` | 工作区冲突时返回 `WORKTREE_CONFLICT` |
| `branch_rename` / `branch_delete` | `name`、`new_name` 或 `force` | `op_id` | 删除未合并分支需要 `force` |
| `branch_merge` | `source`、`mode` | `op_id`、`result` 或冲突 | `result` 为 `up_to_date`、`fast_forward`、`merged`、`squashed`；`mode` 为 `auto`、`no_ff`、`squash` |
| `branch_rebase` | `onto` | `op_id` 或冲突 |  |
| `branch_checkout_remote` | `remote_branch` | `op_id` |  |
| `tag_create` / `tag_delete` / `tag_push` | `name`、`at?` | `op_id` |  |
| `worktree_add` / `worktree_remove` | `path`、`branch` | `op_id` |  |

## 7. 远程操作

抓取、拉取、推送是三个独立的操作，分别对应工具栏上的三个按钮。1.0 只处理名为 `origin` 的远程，多远程管理列入后续版本。

### 7.1 抓取

- 只更新远程分支的位置，不改本地分支和工作区。
- 完成后刷新所有分支的领先落后数，并提示“远程有 N 个新提交，可以拉取”或“远程没有新提交”。
- 客户端在窗口获得焦点时自动抓取一次，最短间隔 5 分钟，可以在设置里关闭。

### 7.2 拉取

拉取有合并和变基两种方式。默认方式按仓库保存，初始值为合并。

| 前置情况 | 行为 |
| --- | --- |
| 落后数为 0 | 提示“远程没有新提交，不需要拉取” |
| 仓库在合并或变基中 | 按钮不可用 |
| 分离 HEAD | 按钮不可用 |
| 工作区有未提交的改动 | 拉取前自动搁置到暂存架，完成或中止后自动放回；放回时能放回的文件先放回，只把有冲突的文件留在暂存架并提示 |

拉取的结果有三种：

1. **本地没有独有提交**：快进，提示“已拉取 N 个提交”。
2. **有独有提交、没有冲突**：合并方式生成一个合并提交；变基方式把本地独有提交改写到远程提交之后。
3. **有冲突**：弹出拉取摘要面板。

拉取摘要面板的内容：

- 标题“拉取完成了一部分，还有冲突要你决定”，副标题写明来源远程分支。
- 拉取方式切换：合并、变基，下方一句话说明所选方式的效果。
- 三个数字：新提交数、已自动合并的文件数、有冲突的文件数。
- 冲突文件列表：路径和冲突类型（几处内容冲突、一边修改一边删除、锁文件）。
- 有未提交改动时，说明它们会先放到暂存架。
- 两个带文字的按钮：“中止，回到拉取之前”和“开始解决”。Esc 等同于中止。

点“开始解决”进入冲突列表（第 8 节）。合并和变基两种方式的区别：

|  | 合并方式 | 变基方式 |
| --- | --- | --- |
| 冲突出现的时机 | 一次全部出现 | 按本地提交逐个出现，顶部显示“变基 · 第 i / n 个提交” |
| 额外操作 | 无 | 跳过当前提交：不把它带到新历史里 |
| 完成后的历史 | 多一个合并提交，说明为“合并 origin/<分支>” | 一条直线，本地提交换成新的哈希 |
| 完成后的领先数 | 原领先数加一 | 等于保留下来的本地提交数 |

拉取的整个过程在操作日志里只记一步。完成后撤销会回到拉取之前，不会停在中间状态。

### 7.3 推送

点推送按钮始终先打开推送对话框，不直接推送。领先数为 0 且没有未推送的标签时，提示“没有需要推送的提交”，不打开对话框。

对话框内容：

- 标题“推送到 origin/<分支>”。
- 要推送的提交列表：短哈希和说明，最新的在上。
- 勾选框“同时推送标签（N 个还没推送）”，没有未推送标签时禁用。
- 勾选框“强制推送（会覆盖远程上的提交）”。
- 警告框，按下表显示。

| 情况 | 警告文字 | 不勾强制推送时点确定 |
| --- | --- | --- |
| 远程有本地没有的提交 | “远程有 N 个你本地没有的提交。不勾选强制推送会被拒绝，建议先拉取。” | 拒绝，提示先拉取 |
| 本地改写了已推送的历史 | “这些提交改写了已经推送过的历史，需要勾选强制推送。” | 拒绝，提示需要强制推送 |
| 其他 | 不显示 | 正常推送 |

强制推送一律使用 `--force-with-lease`：如果远程在上次抓取之后又被别人更新，推送仍然会被拒绝，并提示先抓取。

推送成功后：领先数归零，相关提交的“未推送”标记消失，远程分支标签移到最新提交。推送不能在客户端里撤销，操作时间线里对应的条目不可点击。

### 7.4 其他推送入口

| 入口 | 行为 |
| --- | --- |
| 提交并推送 | 先按 4.4 提交；提交成功后，若远程没有新提交且不需要强制推送，直接推送不弹对话框；否则只提交并提示原因 |
| 推送到这里为止 | 见 5.6；只推送到选中的提交 |
| 推送标签 | 见 6.5；只推送这一个标签 |

### 7.5 认证和网络

- 认证完全交给系统的 Git：SSH 密钥、凭据助手、系统钥匙串。客户端不保存密码或令牌。
- 需要用户输入凭据时，核心层发出 `auth_required` 事件，前端弹出输入框，输入内容只传给这一次 Git 进程。
- 网络操作默认超时 60 秒，进行中在工具栏按钮上显示转动状态，可以取消。

### 7.6 后端命令

| 命令 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `remote_fetch` | `remote?` | `task_id` | 完成后发 `repo_changed`（`refs`） |
| `remote_pull_preview` | `mode` | `incoming`、`auto_merged`、`conflicts[]` | 不改动仓库，用于摘要面板；用内存合并计算 |
| `remote_pull_start` | `mode` | `op_id`、`result` 或进入冲突状态 | 自动搁置工作区改动；`mode` 为 `merge`、`rebase` |
| `remote_push_preview` | 无 | `commits[]`、`unpushed_tags`、`behind`、`needs_force` | 用于推送对话框 |
| `remote_push` | `force`、`tags`、`up_to?` | `task_id` | 被拒绝时返回 `PUSH_REJECTED`，`detail` 注明原因 |
| `auth_reply` | `request_id`、`secret` | 无 | 响应 `auth_required` 事件；内容不记入日志和控制台 |

## 8. 冲突解决

冲突解决分两步：先在冲突列表里按文件处理，需要逐块处理的文件再打开合并窗口。所有修改块都被标记为接受或舍弃后，才能完成。

### 8.1 何时进入

拉取、合并分支、变基、拣选、还原、取回暂存架或贮藏，任何一个产生冲突时都进入同一套流程。进入后整个窗口（工具栏除外）替换为冲突列表，工具栏显示“合并（或变基）进行中 · 还有 N 块没标记”。

“你的”和“对方的”在各场景下的含义：

| 场景 | 你的 | 对方的 |
| --- | --- | --- |
| 拉取（合并）、合并分支 | 当前分支 | 远程分支或被合并的分支 |
| 拉取（变基）、变基 | 正在重新应用的那个本地提交 | 目标分支已有的内容 |
| 拣选、还原 | 当前分支 | 被拣选或被还原的提交 |
| 取回暂存架或贮藏 | 工作区 | 取回的改动 |

Git 在变基时内部的 ours/theirs 和用户的直觉相反，核心层必须按上表转换后再返回，前端不做判断。

### 8.2 冲突列表

一个居中的面板，每个有冲突的文件一行。

| 列 | 内容 |
| --- | --- |
| 文件 | 完整路径 |
| 你的 / 对方的 | 该侧对文件做了什么：已修改、已删除、已新增、已重命名 |
| 状态 | “N 处待处理”、“待选择”（只能整文件二选一的类型）、“已解决” |
| 操作 | 整个文件接受你的、整个文件接受对方的、打开合并窗口 |

列表底部左侧显示进度“已解决 a / b 个文件 · 已标记 x / y 个修改块”，右侧是操作图标：

| 图标 | 行为 |
| --- | --- |
| 跳过（仅变基时显示） | 放弃当前这个本地提交，继续处理下一个 |
| 稍后继续 | 回到主界面，已标记的结果保留；工具栏的提示可以点击返回 |
| 中止 | 放弃整个操作，回到开始之前的状态 |
| 完成 | 校验所有修改块；通过则完成合并 |

最后一个文件变为“已解决”时，自动完成，不需要再点“完成”。

### 8.3 只能整文件处理的冲突类型

这些类型不提供合并窗口，只能在列表里选接受哪一边。两个图标的悬停提示要写明具体结果。

| 类型 | 接受你的 | 接受对方的 | 额外提示 |
| --- | --- | --- | --- |
| 一边修改，一边删除 | 保留文件（或删除，取决于你那边做了什么） | 相反 | 无 |
| 两边都重命名为不同名字 | 用你的文件名 | 用对方的文件名 | 无 |
| 二进制文件 | 用你的版本 | 用对方的版本 | 图片类可点开并排预览（后续版本） |
| 锁文件（按文件名识别，如 `Cargo.lock`、`package-lock.json`、`pnpm-lock.yaml`） | 用你的版本 | 用对方的版本 | 行下方显示“建议：用对方的，完成合并后重新生成” |

### 8.4 合并窗口

以文件形式显示，三栏并排：左边是你的，中间是结果预览，右边是对方的。三栏同步滚动，行与行对齐，各有自己的行号。

- **栏头**（滚动时固定）：左右两栏显示分支名、最新提交的短哈希和作者；中间显示“结果预览”。
- **顶部工具行**：文件路径、整个文件都接受你的、都接受对方的、接受所有没有冲突的修改块、视图切换、撤销、重做、上一处、“第 i / n 处”、下一处、图例。
- **右侧位置标尺**：用色块标出每处修改在文件里的位置，橙色为待处理，绿色为已处理，点击跳转。
- **底部**：左侧显示“这个文件已标记 a / b 个修改块”，右侧是返回列表（叉号）和应用（对勾）。

视图有三种：三栏（默认）、只看两边对比（隐藏结果栏）、只看结果。

### 8.5 修改块

核心层把文件切成两类片段：三方相同的上下文，和有改动的“处”。每一处包含原始内容（双方修改之前），以及一侧或两侧的修改块。

| 类型 | 包含的修改块 | 操作栏标题 |
| --- | --- | --- |
| 冲突 | 你的和对方的各一个 | “冲突 N”和“还有 k 块没标记” |
| 无冲突修改 | 只有一侧 | “修改 N”和“没有冲突，还没标记” |

每一处的上方有一条横向操作栏，分三段对应三栏：

- **左段**（你的修改块）：“修改块 · N 行”、引入这段代码的提交（短哈希、作者、时间、说明）、接受图标（双箭头指向中间）、舍弃图标（红色叉号）。
- **中段**：标题、状态、手动编辑图标。
- **右段**（对方的修改块）：和左段镜像。

修改块的显示：

- 未标记的修改块整块着色（你的橙色，对方的蓝色），左边缘有一条色带，最后一行下方有分隔线。修改块是一个整体，可以是多行，不逐行拆分。
- 两侧行数相同且都未标记时，同一行里不同的片段加深加粗。
- 一侧行数较少时，缺的行用浅色空行补齐，空行没有行号。

### 8.6 标记规则

每个修改块有三种状态：未标记、已接受、已舍弃。

1. 点接受或舍弃后，该修改块立刻变成普通内容：底色、色带、分隔线、行内加粗全部去掉，该侧的两个图标消失。
2. 接受和舍弃在本侧栏里看起来一样，区别只体现在结果栏。
3. 一处里所有修改块都标记后，这一处的整条操作栏消失，三栏在这里都是普通代码。位置标尺上的色块变绿。
4. 标记后不能在原处修改，只能用撤销退回。每次标记都是一个可撤销的步骤。
5. 一处全部标记后，650 ms 后自动滚动到同一文件里下一处未处理的位置；期间用户有其他操作则取消这次跳转。

结果栏的内容按下表计算：

| 你的 | 对方的 | 结果 |
| --- | --- | --- |
| 未标记 | 未标记 | 黄色提示行“待处理：两边的修改块都要接受或舍弃” |
| 已标记 | 未标记 | 已接受的内容（如果有）加黄色提示行“右边的修改块还没标记”；反之同理 |
| 接受 | 舍弃 | 你的内容 |
| 舍弃 | 接受 | 对方的内容 |
| 接受 | 接受 | 先你的，再对方的 |
| 舍弃 | 舍弃 | 原始内容（双方修改之前） |
| 无冲突修改：接受 | — | 该修改块的内容 |
| 无冲突修改：舍弃 | — | 原始内容 |
| 手动编辑过 |  | 用户输入的内容，所有修改块视为已处理 |

### 8.7 其他操作

| 操作 | 规则 |
| --- | --- |
| 整个文件都接受你的（或对方的） | 该文件所有修改块一次标好：选中侧接受，另一侧舍弃；已标记的也会被覆盖；记为一个撤销步骤 |
| 接受所有没有冲突的修改块 | 作用于所有文件里未标记的无冲突修改；没有可处理的时提示；记为一个撤销步骤 |
| 手动编辑 | 弹出编辑框，预填当前结果（还没有结果时填原始内容）；保存后这一处视为已处理 |
| 上一处 / 下一处 | 在当前文件内循环跳转；快捷键 ⌥↑ / ⌥↓；当前所在的一处用强调色描边 |
| 撤销 / 重做 | 退回或重做最近一次标记；一直撤销到头等同于中止 |

### 8.8 校验

- **应用（合并窗口）**：检查当前文件。有未标记的修改块时不应用，底部显示红字“这个文件还有 N 个修改块没有标记，不能应用”，未标记块的操作栏加红框，并跳到第一处。通过则返回列表，该文件显示“已解决”。
- **完成（冲突列表）**：检查所有文件。有未标记的修改块时不完成，底部显示红字“还有 N 个修改块没有标记，不能完成合并”。
- 校验失败的提示在下一次标记使未标记数归零时自动清除。
- 不允许带着未标记的修改块完成，没有“强制完成”的入口。
- 完成时核心层再检查一次结果文件里没有残留的冲突标记（`<<<<<<<`），有则拒绝并返回文件和行号。

### 8.9 完成、中止和恢复

| 动作 | 结果 |
| --- | --- |
| 完成（合并） | 写入结果文件，创建合并提交，回到主界面并选中新提交；自动搁置的工作区改动放回 |
| 完成（变基） | 当前提交处理完后继续下一个；下一个又有冲突则回到冲突列表，进度变为“第 i+1 / n 个提交”；全部处理完后回到主界面 |
| 中止 | 仓库回到操作开始之前，已做的标记全部丢弃；可以用重做回到中止之前的标记状态 |
| 稍后继续 | 标记状态由核心层持久化到磁盘；关闭并重新打开客户端后仍能继续 |
| 完成后撤销 | 整个合并或变基一次退回，不停在某次标记上 |

### 8.10 数据结构和后端命令

核心层返回的冲突会话结构：

```
MergeSession {
  kind: merge | rebase | cherry_pick | revert | unstash
  step: { index, total, commit }      // 仅变基时有
  mine:   { label, commit }           // 已按 8.1 转换
  theirs: { label, commit }
  files: [ConflictFile]
}
ConflictFile {
  path, kind: text | modify_delete | rename | binary | lock
  mine_change, theirs_change          // modified | deleted | added | renamed
  segments: [Context | Change]        // 仅 text 类型
  resolved: bool
}
Context { lines: [string] }
Change {
  id, base: [string]
  mine:   Block | null                // null 表示这一侧没有改动
  theirs: Block | null
  mark: { mine: accept | discard | none, theirs: ..., custom: [string] | null }
}
Block { lines: [string], origin: { commit, author, time, message } }
```

| 命令 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `merge_session` | 无 | `MergeSession` 或空 | 不在冲突状态时返回空 |
| `merge_mark` | `change_id`、`side`、`mark` | 更新后的 `Change` | `mark` 为 `accept`、`discard`、`none`（撤销时用） |
| `merge_mark_file` | `path`、`side` | 更新后的 `ConflictFile` | 整文件接受一侧；对非 text 类型也适用 |
| `merge_accept_non_conflicting` | 无 | 受影响的 `change_id[]` |  |
| `merge_edit` | `change_id`、`lines[]` | 更新后的 `Change` | 手动编辑 |
| `merge_apply_file` | `path` | `resolved` | 有未标记块时返回 `UNMARKED_BLOCKS` 和它们的 `change_id[]` |
| `merge_finish` | 无 | `op_id`，或下一步的 `MergeSession` | 有未标记块返回 `UNMARKED_BLOCKS`；残留冲突标记返回 `CONFLICT_MARKERS` |
| `merge_skip` | 无 | 同上 | 仅变基 |
| `merge_abort` | 无 | `op_id` |  |

标记的撤销和重做由前端维护一个标记历史，逐条调用 `merge_mark` 还原，不进入核心层的操作日志；整个会话完成或中止时才写入一条操作日志。

## 9. 整理提交

整理提交对应 Git 的交互式变基。完整的整理在整理窗口里做；常见的单步操作（撤销、丢弃、并入、压缩）可以在提交上直接执行，不用打开窗口。

### 9.1 可整理范围

从当前分支的最新提交沿第一父提交往回走，遇到以下任一情况停止：

- 合并提交（有两个父提交）；
- 另一个本地分支指向的提交；
- 分支的分叉点（该提交属于主干）。

范围内的提交按从旧到新排列。范围内少于 2 个提交时，提示“可以整理的提交不到 2 个”，不打开窗口。

### 9.2 整理窗口

两个入口：日志过滤栏的整理图标（范围为全部可整理提交），或提交上的“从这里开始整理”（范围为该提交到最新提交）。

窗口里每个提交一行，最早的在最上面。每行有：

- 上移、下移两个图标，第一行的上移和最后一行的下移置灰；
- 三个互斥的处理方式图标：保留（默认）、并入上一个、丢弃；
- 短哈希、说明；
- 已推送的提交显示“已推送”标记。

| 处理方式 | 效果 | 行的显示 |
| --- | --- | --- |
| 保留 | 提交原样保留，可能换新哈希 | 正常 |
| 并入上一个 | 改动合并到它上面最近的一个被保留的提交，它的说明追加到那个提交的正文 | 向右缩进 |
| 丢弃 | 提交和它的改动都去掉 | 说明加删除线并变灰 |

规则：

- 第一行选“并入上一个”时，上面没有可并入的提交，按“保留”处理。
- 窗口底部实时显示“N 个提交整理后变成 M 个”。
- 范围内有已推送的提交时，底部增加一句“其中有已经推送的提交，整理后需要强制推送”。
- 全部丢弃是允许的，结果是分支退回到范围之前的那个提交。
- 1.0 不在窗口里改说明；要改说明，整理完成后对最新提交用“修改提交说明”，或用 Squash Into。

点确定后：

1. 核心层按顺序重放提交。重放中遇到冲突时进入冲突解决（第 8 节），类型为变基。
2. 范围内的提交换成新的哈希，全部标记为未推送，领先数重新计算。
3. 改写了已推送的提交时，分支标记为“需要强制推送”，落后数显示为 0。
4. 提示“N 个提交整理成了 M 个”，带撤销图标。整个整理是一个撤销步骤。

### 9.3 快捷整理操作

这些操作内部都是一次只含固定指令的整理，规则和 9.2 的第 2–4 步相同。可用条件见 5.6。

| 操作 | 等效的整理 | 额外效果 |
| --- | --- | --- |
| 撤销提交 | 丢弃最新提交 | 它的改动放回工作区并保持勾选 |
| 丢弃提交 | 丢弃选中的提交，其后的提交保留 | 改动不保留 |
| Fixup | 把提交面板里勾选的改动并入选中的提交，其后的提交保留 | 勾选的文件从提交面板移除；说明不变 |
| Squash Into | 同 Fixup | 先弹出输入框修改该提交的说明 |
| 压缩提交（多选） | 选中提交里除最早一个外都设为“并入上一个” | — |
| 丢弃提交（多选） | 选中的提交都设为“丢弃” | — |

### 9.4 后端命令

| 命令 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `rebase_range` | `from?` | `commits[]`、`has_pushed` | 返回可整理范围；`from` 为空时返回最大范围 |
| `rebase_apply` | `steps[]` | `op_id`、`result`，或进入冲突状态 | 每个 step 为 `{ id, action, message?, extra_selection? }`；`action` 为 `pick`、`squash`、`drop`；`extra_selection` 用于 Fixup 并入工作区改动 |

快捷操作不单独设命令，前端按 9.3 构造 `steps` 后调用 `rebase_apply`。核心层需要校验：`steps` 必须恰好覆盖范围内从某个提交到最新提交的连续一段，否则返回 `INVALID_RANGE`。

## 11. 撤销、重做和操作时间线

客户端执行的每个写操作都记入操作日志，用户可以一步步退回，也可以直接回到某一步之前。这是产品的核心承诺，所有写命令都必须接入。

### 11.1 交互

| 入口 | 行为 |
| --- | --- |
| 工具栏的撤销图标 | 撤销最近一步；没有可撤销的步骤时置灰 |
| 工具栏的重做图标 | 重做最近一次被撤销的步骤；执行任何新的写操作后，重做列表清空 |
| 提示条上的撤销图标 | 撤销刚刚完成的这一步 |
| 操作时间线（日志底部） | 显示最近 5 步，最新的在左；点某一步，回到这一步之前（这一步和它之后的全部撤销） |

- 撤销后提示“已撤销：<操作名>”；一次退回多步时提示“已退回到“<操作名>”之前”。
- 一次退回多步在重做列表里算一项，重做会一次恢复。
- 仓库在合并或变基中时，工具栏的撤销作用于冲突标记（见 8.7）；标记撤完后再撤销等同于中止。

### 11.2 哪些操作可以撤销

| 类别 | 操作 | 可撤销 |
| --- | --- | --- |
| 提交类 | 提交、修订、修改说明、拣选、还原、重置、撤销提交、丢弃提交、Fixup、压缩、整理提交 | 是 |
| 分支类 | 新建、切换、重命名、删除、合并、变基、检出远程分支、检出指定版本 | 是 |
| 标签和工作目录 | 新建标签、删除标签、新建和移除工作目录 | 是 |
| 工作区类 | 丢弃改动、回滚、搁置、取回、删除搁置、贮藏、取回贮藏、丢弃贮藏、加入版本控制、加入忽略规则、删除未跟踪文件 | 是 |
| 拉取 | 拉取（含冲突解决的整个过程） | 是，整个过程算一步 |
| 对外类 | 推送、推送标签、推送到这里为止 | 否；时间线里显示但不可点击 |
| 只读和偏好 | 抓取、过滤、收藏、显示选项 | 不记入时间线 |

推送之后，它之前的步骤仍然可以撤销，但撤销会让本地落后或偏离远程。这种情况下撤销前弹出确认，说明“这一步已经推送，撤销后需要强制推送才能让远程一致”。

### 11.3 操作日志的实现要求

核心层在每个写命令执行前后各记一次快照，写成一条日志。

```
OpEntry {
  id, label, kind, time
  before: Snapshot
  after:  Snapshot
  undoable: bool
}
Snapshot {
  head: 分支名 或 分离的提交
  refs: { 引用名: 提交哈希 }        // 本地分支和标签
  index_tree: 索引对应的树对象
  worktree_tree: 工作区已跟踪文件对应的树对象
  untracked: 被这次操作影响的未跟踪文件的备份位置
  shelf / stash: 列表状态
}
```

- 快照用 Git 对象库保存树对象，并在 `refs/strand/ops/<id>` 下留引用，避免被垃圾回收。
- 撤销 = 把仓库恢复到 `before`；重做 = 恢复到 `after`。恢复顺序：引用、HEAD、索引、工作区、暂存架和贮藏。
- 恢复前检查仓库当前状态是否等于该条日志的 `after`（撤销时）或 `before`（重做时）。不一致说明仓库被客户端之外的工具改过，返回 `STATE_DIVERGED`，前端提示“仓库在别处被修改过，这一步不能自动撤销”，并把该条及更早的日志标记为不可撤销。
- 日志按仓库保存在应用数据目录，保留最近 200 条或 30 天，超出的连同快照引用一起清理。
- 重启客户端后日志仍然有效，重做列表不保留。

### 11.4 后端命令

| 命令 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `oplog_list` | `limit` | `entries[]`、`can_undo`、`can_redo` | 每条带 `id`、`label`、`time`、`undoable` |
| `oplog_undo` | `to_id?` | 被撤销的 `entries[]` | `to_id` 为空时撤销一步；否则撤销到该条（含）为止 |
| `oplog_redo` | 无 | 被重做的 `entries[]` |  |

所有写命令的返回值里都带 `op_id` 和 `label`，前端用它们生成提示条和时间线条目。`label` 由核心层生成，格式固定，例如“提交“<标题>””“切换到 <分支>”“重置到 <短哈希>”。

**实现说明（和上面不一样的地方）**

- 日志存在仓库的 `.git/strand/oplog.json`，没有放在应用数据目录：核心层不依赖 Tauri，放在仓库里自然按仓库分开。每条日志在 `refs/strand/ops/<id>` 下留一个提交（树里放四棵快照树，父提交是这一步前后的提交），日志和分支列表都不显示它。
- 快照只包括 HEAD、本地分支和标签、索引树、工作区已跟踪文件的树。另外记下贮藏列表和暂存架里没删除的条目：撤销取回贮藏时贮藏条目会回来（清空后用 git stash store 按原顺序和说明重建），撤销取回或删除搁置时条目会回来。未跟踪文件不在普通快照里；加入版本控制、加入忽略规则、删除未跟踪文件这三个操作额外记下涉及的文件（不管跟踪与否，存成一棵树），新建和移除工作目录额外记下链接的工作目录列表（`OpScope`），这样它们也能撤销。注解标签对象不额外保留
- 恢复前的核对按引用和文件分开做：HEAD 和这一步改过的引用必须还是这一步结束时的位置；文件只恢复这一步改过的那些，用户之后在别的文件上的改动保留，同一个文件又被改过时才返回 `STATE_DIVERGED`（`detail.files` 列出冲突的引用和文件）。要写出的文件在磁盘上是内容不同的未跟踪文件时也算冲突。说明书要求整个快照一致，那样用户改了任何文件之后都不能撤销。
- 不用等到点撤销才发现外部修改：每次读时间线（`oplog_list`，引用或工作区变化时都会重新读）都核对最近一步改过的 HEAD、引用、索引条目、文件、贮藏和暂存架，在别处被改过时这一步和更早的步骤显示为不能撤销，原因写明是哪一项（如“main 在别处被修改过”“a.txt 在别处被修改过”），工具栏撤销图标置灰、悬停显示原因。这个标记不写进日志，外部又改回去就恢复；点撤销时的完整核对照旧，失败时才写进日志。
- 撤销越过已推送的步骤时返回 `ALREADY_PUSHED`，前端确认后带 `confirm_pushed` 再调用。
- 合并或变基进行中时，工具栏的撤销、重做和时间线都置灰，冲突标记在合并窗口里撤销；没有做“标记撤完再撤销等同于中止”。
- 写命令返回 `op`（`id`、`label`、`kind`、`time`、`undoable`、`undone`）代替 `op_id`；`label` 由命令层（src-tauri）生成。
- 已接入的操作：11.2 表里的全部操作（推送只显示）。中止合并不记日志。`tests/undo_all.rs` 逐个做一遍，核对撤销后和操作前、重做后和操作后完全一致（HEAD、引用、索引、贮藏、暂存架、工作区每个文件含未跟踪文件、链接的工作目录）；这个测试找出了一处错误：撤销“加入版本控制”会把这个文件从磁盘上删掉，已修正。

## 13. 数据模型

前后端之间传递的主要结构如下。字段名用下划线命名，时间用 Unix 秒，哈希用完整的 40 位字符串，短哈希由前端截取前 7 位显示。

```
RepoState {
  path, name
  head: { kind: branch | detached | unborn, branch?, commit? }
                              // unborn：新仓库还没有任何提交，此时没有 commit
  state: normal | merging | rebasing | cherry_picking | reverting | unstashing
  // 默认拉取方式不在这里，由前端按仓库保存
}

Commit {
  id, parents: [id]
  title, body
  author: { name, email }, time
  refs: [Ref]                 // 指向该提交的引用
  unpushed: bool              // 从当前分支能到达、但不在它的跟踪分支里
  is_merge: bool
}
Ref {
  kind: head | branch | remote | tag   // head 只在分离 HEAD 时出现
  name                        // 短名，如 main、origin/main、v0.4.0；不含 origin/HEAD
}

LogPage {                     // log_query 的返回
  offset                      // 实际起始行（超出范围时会被截到 total）
  rows: [Commit]              // 单次最多 500 行
  graph: [GraphRow]           // 与 rows 一一对应
  total                       // 日志总行数
  lanes: int                  // 整个日志用到的最大泳道数，前端据此定图谱列宽
}

GraphRow {
  lane: int                   // 本行提交所在的泳道，从 0 开始
  edges: [{ from_lane, to_lane, kind: straight | fork | merge }]
                              // 从本行画到下一行的全部线段，包括只从本行经过的泳道
                              // straight：同一泳道往下；fork：第一个父提交在别的泳道，线汇过去
                              // merge：合并提交连向第二个及以后的父提交
}

GitInfo {                     // git_check 的返回
  found: bool, version?, ok: bool, min_version
}

CommitCaps {                  // 每项为 { ok: bool, reason?: string }
  cherry_pick, revert, reset, undo, reword, fixup, drop,
  rebase_from, push_up_to, compare_local, open_in_browser
}

FileChange {
  path, old_path?             // 重命名时有 old_path
  status: M | A | D | R
  added, deleted: int
  binary: bool
}

Hunk {
  title                       // 函数或结构名 + 起始行
  lines: [{ kind: context | add | del, old_no?, new_no?, text }]
}

Selection {                   // 提交、搁置、补丁共用
  files: [{ path, whole: bool, lines?: [{ hunk, line }] }]
}

Branch {
  name, head: id
  upstream?: 远程分支名
  ahead, behind: int
  needs_force: bool           // 本地改写了已推送的历史
  favorite: bool
  is_current: bool
}
RemoteBranch { name, head: id }
Tag { name, at: id, pushed: bool }
Worktree { path, branch }

ShelfEntry { id, name, time, files: [FileChange] }
StashEntry { index, message, time, files: [FileChange] }
```

前端自己维护、不经过核心层的状态：当前标签页、选中的提交和多选、过滤条件、分支树的展开状态、提交面板的勾选、提交说明草稿、比较起点、冲突标记的撤销历史。

按仓库持久化的偏好（存在应用数据目录）：拉取方式、提交选项、说明历史、收藏的分支、日志显示选项、按目录分组、差异视图模式。

## 14. 错误码

所有命令失败时返回 `{ code, message, detail }`。前端的处理方式按下表，没有列出的错误码一律用提示条显示 `message`。

| 错误码 | 含义 | 前端处理 |
| --- | --- | --- |
| `REPO_BUSY` | 有写操作正在执行 | 提示“上一个操作还没完成”，不重试 |
| `MERGE_IN_PROGRESS` | 仓库在合并或变基中，该操作不允许 | 提示并提供“打开冲突列表” |
| `NOTHING_SELECTED` | 提交或搁置时没有选中内容 | 提示“至少勾选一个文件” |
| `EMPTY_MESSAGE` | 提交说明为空 | 提示并把焦点移到输入框 |
| `ALREADY_PUSHED` | 目标提交已推送，不能改写 | 提示原因 |
| `INVALID_NAME` | 分支或标签名不合法或重名 | 在输入框下方显示 `message`，对话框不关闭 |
| `INVALID_RANGE` | 整理的步骤和仓库当前状态对不上 | 提示“仓库已变化，请重新打开整理窗口”，并刷新 |
| `WORKTREE_CONFLICT` | 切换分支时工作区改动会被覆盖 | 弹出询问：先贮藏再切换，或取消 |
| `CONFLICTS` | 操作产生冲突，已进入冲突状态 | 不算错误：打开冲突列表 |
| `UNMARKED_BLOCKS` | 还有未标记的修改块 | 按 8.8 显示红字和红框，跳到第一处 |
| `CONFLICT_MARKERS` | 结果里残留冲突标记 | 提示文件和行号，打开该文件的合并窗口 |
| `PUSH_REJECTED` | 推送被远程拒绝 | 按 `detail.reason`（`behind`、`needs_force`、`lease_stale`、`protected`）显示对应说明 |
| `AUTH_FAILED` | 认证失败 | 提示并允许重新输入凭据 |
| `NETWORK` | 网络不通或超时 | 提示并提供“重试” |
| `STATE_DIVERGED` | 撤销或重做时仓库状态和日志不一致 | 按 11.3 提示，并刷新时间线 |
| `NOT_FOUND` | 提交、分支、标签或文件不存在 | 提示并刷新对应区域 |
| `CANCELLED` | 任务被取消 | 不提示 |
| `GIT_FAILED` | Git 命令返回了未归类的错误 | 提示 `message`，并提供“在控制台查看” |
| `NOT_A_REPO` | 选中的文件夹及其上级都不是 Git 仓库 | 在打开仓库页显示 message，可以重新选择 |
| `NO_REPO` | 还没有打开仓库就调用了需要仓库的命令 | 属于前端时序错误；回到打开仓库页 |
| `GIT_MISSING` | 需要系统 Git 的操作找不到 Git 或版本过低 | 提示安装或升级 Git，并给出下载地址 |
| `INVALID_REGEX` | 日志搜索打开了正则，表达式写得不对 | 搜索框变为错误样式，列表显示“正则表达式写得不对”和清空过滤条件 |

## 15. 性能和其他非功能要求

性能指标以一个 10 万提交、工作区 5 万文件的仓库为基准，在 2020 年以后的主流笔记本上测量。这些是目标值。已经逐项实测（本机发布版，Apple 芯片笔记本）。测试仓库用 scripts/gen\_perf\_repo.py 生成，核心层的计时用 crates/strand-core/examples/perf.rs，界面的计时在桌面应用里用临时自测代码量。按用户要求，最终验收用的是 1 万提交、5 千文件的仓库；10 万提交、5 万文件的仓库上也测过核心层，结果附在后面。

1 万提交、5 千文件（全部达标）：打开仓库到第一屏日志 219 ms；快速滚动 60 帧每秒，没有出现空白行，新一页数据 2 ms 内返回；文件变化后 154 ms 反映到提交面板；打开 2000 行改动的差异 28 ms；搜索首批 15 ms，按路径过滤首批 206 ms；逐行追溯 5000 行文件首屏 224 ms、全部 489 ms；在界面里提交 1 个文件 146 ms、切换分支约 100 ms、重置约 110 ms；空闲内存（打开仓库后不操作，四个进程合计）RSS 232 MB、按“活动监视器”的内存（footprint）算 110 MB，其中只有一个提交的小仓库是 209 MB / 91 MB（Tauri 加系统 WebKit 本身的开销）。

10 万提交、5 万文件（核心层）：打开仓库加第一屏 97 ms（有 commit-graph）；状态 116–128 ms；差异约 20 ms；搜索 100 ms；逐行追溯首屏 260 ms；提交 485 ms、切换到相距 10 个提交的分支 389 ms、重置 453 ms；切换到相距很远、约 4 万个文件要改写的分支约 600 ms（其中 git switch 本身约 260 ms）；按路径过滤（不区分大小写的子串匹配用不上路径过滤器）稀疏的路径首批约 0.5 秒、全部要十几秒，结果边找边显示。

| 场景 | 目标 |
| --- | --- |
| 打开仓库到看到第一屏日志 | 1 秒以内 |
| 日志滚动 | 保持 60 帧每秒，新一页数据 50 ms 内返回 |
| 工作区状态刷新（文件变化后） | 300 ms 内反映到提交面板 |
| 打开一个 2000 行改动的差异 | 200 ms 以内 |
| 过滤或搜索日志 | 首批结果 300 ms 内返回，其余分批追加 |
| 逐行追溯一个 5000 行的文件 | 首屏 500 ms 内，其余后台加载 |
| 本地写操作（提交、切换分支、重置） | 500 ms 以内完成并刷新界面 |
| 空闲内存占用 | 300 MB 以内 |

实现要点：

- 所有 Git 操作在后台线程执行，界面线程不阻塞。超过 300 ms 的操作显示进行中状态。
- 日志优先读取仓库的 commit-graph 文件；没有时在后台生成。
- 工作区状态用文件监听做增量刷新，不定时全量扫描。
- 向前端传大量行数据时分批发送，单批不超过 500 行。

其他要求：

| 方面 | 要求 |
| --- | --- |
| 平台 | macOS 12 及以上、Windows 10 及以上；两个平台功能一致。Linux 不在 1.0 范围内 |
| Git 版本 | 网络和变基操作依赖系统安装的 Git，最低 2.30；启动时检测，缺失或版本过低时提示 |
| 数据安全 | 任何会丢失改动的操作执行前都先写入操作日志快照；快照写入失败则不执行操作 |
| 外部修改 | 用户同时用命令行或其他工具操作仓库时，界面要能正确刷新，不崩溃、不覆盖外部的改动 |
| 凭据 | 不保存、不记录、不显示在控制台 |
| 语言 | 1.0 为简体中文；界面文字全部走资源文件，为后续翻译留口 |
| 日志 | 核心层写本地日志文件，保留 7 天，用于排查问题；不上传 |

## 16. 验收要点

每个模块交付时至少通过下列检查。原型配套的 172 项流程测试可以作为前端交互的参考用例。

- [x] **提交**：勾选部分文件和部分行提交后，提交内容和勾选一致，未勾选的改动仍在工作区。
- [x] **修订**：对上一次提交和更早的未推送提交都能修订；已推送的提交被拒绝。
- [x] **暂存架和贮藏**：搁置后取回，工作区内容和搁置前逐字节一致。
- [x] **日志**：四个过滤器、正则和大小写开关、按时间排序都能单独和组合生效。
- [x] **提交操作**：5.6 的每个操作在满足和不满足条件时分别可用和置灰，置灰时有原因说明。
- [x] **分支**：新建、切换、重命名、删除、合并（三种结果）、变基、检出远程分支、检出指定版本全部可用。
- [x] **拉取**：快进、无冲突合并、有冲突三种情况；合并和变基两种方式；工作区改动自动搁置和放回。
- [x] **推送**：正常推送、远程有新提交时被拒绝、改写历史后必须强制推送、强制推送使用带租约的方式。
- [x] **冲突解决**：8.6 结果表的每一行；标记后高亮和按钮消失；有未标记块时不能应用、不能完成；中止后仓库回到开始之前。
- [x] **整理提交**：保留、并入、丢弃、调整顺序的组合；范围内有已推送提交时给出警告并标记需要强制推送。
- [x] **撤销和重做**：11.2 列为可撤销的每个操作，撤销后仓库状态和操作前一致，重做后和操作后一致。
- [x] **外部修改**：在命令行里提交、切换分支、修改文件后，界面在 1 秒内刷新，受影响的撤销步骤被标记为不可撤销。
- [x] **无障碍**：不用鼠标可以完成提交、拉取、解决一个冲突、推送的完整流程。
- [x] **主题**：浅色和深色下所有界面文字对比度达到 4.5:1。

验收记录（2026-11-14）：核心层测试 134 项全部通过，对应关系如下。
- 提交：`lines.rs` commit_only_some_lines、`worktree.rs` commit_only_selected_files。
- 修订：`amend.rs`（上一次提交、部分行、已推送被拒绝）；更早的未推送提交用 Fixup / Squash Into，见 `rebase.rs` fixup_and_squash_into。
- 暂存架和贮藏：`stash.rs` shelf_roundtrip_is_byte_identical 等 8 项。
- 日志：`log_filter.rs` 7 项（文字、正则、大小写、分支、作者、日期、路径组合，按时间排序）。
- 提交操作：`commits.rs` unpushed_and_caps、`remote.rs` push_to_caps 核对每个操作在满足和不满足条件时的 `caps` 和原因；界面按 `caps` 置灰并在悬停里显示原因。
- 分支：`branches.rs`、`merge_mode.rs`、`branch_rebase.rs`（合并的快进、合并提交、冲突三种结果，以及三种合并方式）。
- 拉取：`remote.rs` pull_fast_forward_merge_and_rebase、pull_conflict_then_abort、pull_shelves_local_changes 等。
- 推送：`remote.rs` push_preview_and_push、push_rejections_and_force（强制推送用 --force-with-lease）。
- 冲突解决：`conflict.rs` 单元测试 result_table_rows 覆盖 8.6 表的每一行，集成测试覆盖未标记时不能应用和完成、手动编辑、中止。
- 整理提交：`rebase.rs` 6 项，pushed_commits_in_range_warn_and_need_force 覆盖已推送警告和整理后需要强制推送。
- 撤销和重做：`undo_all.rs` every_undoable_operation_round_trips 覆盖 11.2 的每个可撤销操作。
- 外部修改：`oplog.rs` external_changes_mark_affected_steps；桌面应用实测，命令行提交、切换分支、修改文件后，界面在 140～190 ms 内刷新，撤销图标随即置灰，并显示“main 在别处被修改过”“HEAD 在别处被修改过”。
